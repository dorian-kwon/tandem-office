# 완성본 번역 위키 구현 계획

**목표**는 저장이 확정된 완성본의 표현을 다음 번역에 재사용하고 ‘위키 보기’로 해당 보관함을 Obsidian에서 여는 것이다. Electron 셸이 문서의 확정 시점을 알려 주고, 별도 작업자가 구조 읽기·SQLite 색인·Markdown 페이지 생성을 맡는다. 단계별 실행에는 `superpowers:executing-plans` 또는 독립된 작업의 `superpowers:subagent-driven-development`를 사용한다. [채택한 설계](../specs/2026-11-20-contextual-editing-wiki-design.md)

### 1. 완료 판 기록과 재개

- [ ] `apps/shell/src/main/translate/wiki-store.ts`와 `apps/shell/tests/translation-wiki-store.test.ts`에서 문서 ID와 판 ID의 결합을 고유 키로 사용한다. 처음 저장되지 않은 탭, 닫기 취소, 내보내기 실패는 0건, 같은 판을 내보내고 닫으면 1건인 사례부터 테스트한다.
- [ ] `tab-manager.ts`, `window-close-guard.ts`, `translate/export-translation.ts`의 실제 성공 경로에서 기록한다. 미저장 상태에서 다른 문서로 나가면 디스크에 확정된 판만 고려한다. 미리보기 탭·일시적 포커스 이동과 구분한다. 앱 종료 시에는 작업자 분석을 기다리지 않고 최소 대기 기록의 내구성만 확보한다.
- [ ] `pending → processing → complete` 전이에 실패 후 재개와 제외 상태를 추가한다. 활성 판 교체와 색인 갱신을 한 트랜잭션에 넣는다. 중단된 판을 복구하고 새 판이 먼저 도착하면 옛 결과가 덮어쓰지 못하게 한다. 재실행·잠금·파일 교체·삭제·디스크 부족을 주입해 확인한다.

### 2. 문서 읽기와 위키 페이지 생성

- [ ] `apps/shell/src/main/translate/wiki-worker.ts`는 기존 `file-index/extract-worker.ts`의 격리 방식을 참고한다. 형식별 위치를 보존하고, 이미 가린 정보는 기존 `packages/file-parse/src`의 가림 규칙을 따른다. 중첩 셀과 그룹을 재귀 탐색하되 문서별 작업을 묶어 처리한다.
- [ ] 대응이 입증된 원문과 번역만 짝지어 저장한다. 번역문만 있으면 문체·구성 사례를 만든다. 동일 문구가 서로 다른 셀에 있는 예, 행을 합친 번역, 스캔 PDF에 OCR 결과가 없는 예를 검사한다.
- [ ] 의뢰 기관·산업·문서 종류·언어 방향·문장 역할과 출처 위치를 기록한다. 발주처를 추론할 근거가 없으면 미분류다. 최초·동일 판·개정판별 페이지와 링크를 대조한다. 앱 전용 파일·영역만 원자적으로 갱신하고, 사용자가 수정한 부분과 직접 만든 노트는 보존한다.

### 앱 내장 스킬 ‘번역 위키 정리’

- [ ] 앱에 내장하는 `apps/shell/resources/builtin-skills/translation-wiki/SKILL.md`에 **자료의 자격, 분류, 용례 추출, 기존 항목과의 대조, 출력 예시**를 담는다. 완성본의 제한된 구절, 섹션·표 위치, 언어 방향, 확인한 기관, 후보 페이지 ID만 입력으로 받는다. 새 고객의 문서 사례를 추가할 때마다 스킬 파일을 다시 작성할 필요는 없다.
- [ ] 각 제안은 항목 종류(용어·문체·병렬 예문), 적용 범위, 입증하는 문서 판과 위치, 인용 구절, 기존 페이지에 사례 추가 또는 별도 사례 보존 여부를 반환한다. 근거가 부족하면 판단을 보류한다. 단일 출현과 사용자가 지정한 규칙을 구분한다. 기존 지침과 충돌하거나 다른 기관에서 뜻이 달라질 때 이를 명시한다. 텍스트 속 지시문은 정리 대상 자료로만 취급한다.
- [ ] 검증 예시는 부산시 관광 일정표의 한영 병기 셀, 영문 일정표만 남은 경우, 발주처가 다른 동일 용어, 같은 문서의 재내보내기로 구성한다. 첫 사례는 검증된 대응쌍을, 두 번째는 표기·문체 용례를, 세 번째는 각 기관 범위의 별도 사례를 반환해야 한다. 마지막은 근거 건수가 늘어나면 실패다.
- [ ] 일상적인 나가기·닫기·내보내기는 로컬 작업자만 예약한다. 자동으로 복원할 수 있는 구조·문서 근거는 코드가 기록한다. 의미 판단에 모델을 사용하는 ‘AI로 위키 정리’는 사용자가 선택한 대상에만 스킬을 적용하는 안을 기본으로 둔다. 모델의 제안은 앱이 범위·출처·판과 실제 인용문을 검증한 뒤에만 반영한다. 파일 쓰기·중복 방지·Obsidian 열기와 재시작 복구는 앱의 책임이다.

### 3. 다음 번역에 예문 넣기

- [ ] `translate/context-injection.ts`와 `apps/shell/tests/translate-context-injection.test.ts`에서 검색 비활성·검색 시간 초과·검색 결과 없음의 기존 출력을 비교한다. 프로젝트 밖 단일 문서의 번역·다듬기에도 같은 조회 경계를 적용한다.
- [ ] 언어 방향·고객별 접근 범위를 먼저 제한하고 실제 번역 묶음에서 어휘·문서 종류·문장 역할로 순위를 정한다. 현 용어집·명시 지침을 우선하고, 출처 ID와 제한된 예문을 기존 참고자료 예산 안에 함께 넣는다. 현재 셀의 열 제목·인접 문맥과 과거 예문을 구분한다.
- [ ] 용어집과 과거 예문이 충돌하는 사례, 다른 기관의 독점 용어 유출, 유사한 문장의 수치·연도 오복사, 미분류 문서와 범용 문체 검색을 각각 검사한다. 원본 링크로 돌아가기, 분류 정정, 사례 제외·삭제는 다음 검색에도 반영해야 한다.

- [ ] 번역 요청에는 전권 개요·고정 표기, 절 양쪽의 원문, 확정된 번역의 근처 표현을 현재 배치 문맥으로 결합한다. 같은 절에서 병렬 처리된 두 묶음의 경계는 완료 뒤 함께 점검한다. 제목·관광 소개·표 일정·안전 지침을 섞은 독립 평가 문서에 멀리 떨어진 약칭 정의, 다음 문단에서만 확인되는 지시 대상, 반복 서두와 의도적 병렬 구절을 넣는다. 의미·서식 보존과 실제 수정 단위별 Undo/Redo, 재개 후 사용자 수정 보존을 함께 검증한다.

- [ ] 전권 번역의 단위 수집 시 원문 지문별 위치·문장 역할을 색인한다. 다음 배치에 직전 원문·실제 반영된 번역과 관련된 과거 반복 용례를 읽기 전용으로 전달한다. 동일 문구의 같은 역할·다른 역할, 1차 배치 뒤 사용자 편집·Undo·중단 재개, 다른 절에서 아직 완료되지 않은 병렬 결과를 검사한다. 현재 배치의 ID 외에는 쓰지 않고, 반복 문장도 위치마다 독립 Undo가 되는지 검증한다.

### 4. 위키 보기 → Obsidian → 우리 위키

- [x] `apps/shell/src/renderer/src/translate/ProjectDetail.tsx`와 단독 번역 화면에 같은 **위키 보기** 동작을 연결한다. 셸 IPC는 현재 프로필의 보관함과 고정된 공식 다운로드 경로만 열도록 한다. 빈 위키의 시작 페이지를 즉시 준비하며 전체 색인을 기다리지 않는다.
- [x] `apps/shell/src/main/translate/open-wiki.ts`에서 설치·프로토콜·보관함 등록 상태를 구분한다. 등록된 보관함의 시작 파일 URI는 `'obsidian://open?path=' + encodeURIComponent(indexPath)`로 만든다. 미등록 보관함은 공식 vault manager와 실제 폴더 경로로 최초 연결을 돕는다.
- [x] 미설치 시 OS·아키텍처에 맞는 공식 다운로드를 바로 호출한다. 다운로드 요청과 설치 성공을 구분한다. 돌아왔을 때 설치가 확인되면 보류한 위키 열기를 한 번 재개한다. 오프라인·취소·다른 실행 오류가 다운로드 루프를 만들지 않는지 검사한다.
- [x] `apps/shell/tests/open-wiki.test.ts`에서 외부 실행을 가짜로 교체해 기존 설치·첫 연결·미설치·설치 후 복귀·같은 이름의 보관함·한글 경로·중복 클릭을 검사한다. 실제 PC 최초 연결에서는 설치 파일, 올바른 보관함의 시작 페이지, 링크 이동까지 대조한다.

macOS에서는 현재 설치된 Obsidian의 프로토콜 등록과 실행 경로를 확인했다. 설치본의 앱 코드를 격리한 Electron에서 처음 폴더 선택과 URI 전달을 시험 입력으로 대체해 보관함 등록, 한글·공백·특수문자가 있는 시작 페이지, 여섯 분류 링크와 돌아가기를 검증했다. Windows·Linux 설치 경로와 설치 후 복귀는 모의 환경에서 검증했다. 실제 설치 파일 목록은 공식 릴리스와 대조했다.

### 5. 회귀와 품질 판정

- [ ] `npm test -w @genoffice/shell -- translation-wiki-store open-wiki translate-context-injection export-translation`과 `npm run typecheck -w @genoffice/shell`을 실행한다. 정상 경로와 복구 경로 양쪽이 통과해야 한다. 화면 문구는 기존 언어 리소스 규칙을 따른다.
- [ ] `e2e/supported-document-formats.spec.ts`의 19종을 숨김 모드에서 검사한다. 최소 fixture와 별도로 부산 DOCX·용어집, 500쪽 HWP·HWPX·PDF, 대용량 시트로 번역·닫기·재실행·검색·단위별 Undo/Redo를 확인한다.
- [ ] 완성본 100편·사례 10만 건으로 기능 켬·끔을 교차 비교한다. 입력·스크롤 추가 p95 16.7ms 이내, 위키에서 발생한 50ms 이상 UI 작업 0건을 확인하고 열기·저장·닫기·CPU·메모리도 함께 기록한다.
- [ ] 독립된 한↔영 평가 문서를 준비해 용어집만 쓴 조건, 예문 1개, 최대 5개, 문맥 순위까지 적용한 조건을 비교한다. 문서별로 원 평가셋과 기억 저장소의 중복을 제거하고, 용어·문체·뜻·수치 보존·다른 기관 표현 유입을 가려서 평가한다. 실제 결과로 기본 검색 예산을 결정한다.
