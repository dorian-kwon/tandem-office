# 저사양 PC의 문서 열기와 입력 성능 개선 계획

대상은 v0.15.7에서 측정한 일곱 경로다. Electron 메인 스레드가 맡은 색인 작업을 워커로 옮기고, 각 편집기에서 화면을 갱신할 때 처리하는 문서의 양을 줄인다. TypeScript, ProseMirror, React, SQLite와 기존 문서 엔진을 사용한다.

| 작업         | 구현 범위                                                                                                                                                           | 검증 기준                                                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 워드 첫 화면 | apps/docs/src/renderer/phased-content.ts에서 표의 내부 노드 수를 첫 표시와 후속 묶음 크기에 반영한다. 표 단위 경계, 편집 중 변경, 저장 대기와 실행 취소를 보존한다. | 일반 문단 122쪽의 기존 분할 테스트와 중첩 표 테스트를 실행한다. 부산 가이드북의 첫 표시, 마지막 블록 도착 및 저장 후 재열기를 확인한다. |
| AI 입력      | 워드 선택 범위의 가림 결과를 문서 버전과 선택 위치별로 재사용한다. 여러 편집기에서 이전 답변의 탐색 설정과 스트리밍 상태를 재사용한다.                              | 선택 변경, 가림 표시 수정, 완료된 답변의 링크 및 도구 상태 전환을 확인한다.                                                             |
| PDF 스크롤   | apps/pdf/src/renderer/App.tsx에서 행별 시작 위치와 표시 페이지 번호를 캐시하고 현재 행을 이진 탐색한다.                                                             | 스크롤 경계, 혼합 크기, 회전, 줌, 양면 보기와 페이지 순서 변경을 검사한다.                                                              |
| 검색 색인    | apps/shell/src/main/file-index에서 본문 토큰화와 SQLite 쓰기를 워커에서 실행하고 큐의 쓰기 순서를 유지한다.                                                         | 검색 결과, 재색인, 삭제, 클라우드 파일 이름만 색인, 종료와 실패 복구를 확인한다.                                                        |
| HWP 열기     | apps/hwp/src/main에서 동일한 HWP 컨테이너와 구역 레코드를 변경 추적·구역·필드 검사에 공유한다.                                                                      | 변경 추적의 정리 실패, 메모·캡션·필드 보존, HWPX 구분을 검사한다. 64MiB 사본으로 비교한다.                                              |

각 작업은 담당 파일 범위 안에서 구현하고 관련 Vitest와 타입 검사를 실행한다. 통합 후 변경된 파일의 형식과 정적 검사를 확인한다. 고객 문서는 로컬에서만 사용한다. GUI 측정은 창이 보이지 않는 방식으로 진행한다.

## 구현 결과와 확인 방법

- 부산 가이드북 원본과 영문 DOCX를 숨김 Chromium에서 열었다. CPU 속도를 4배 느리게 설정했을 때 영문본의 첫 편집 화면에 들어가는 블록은 82개에서 4개로, DOM 요소는 14,507개에서 132개로 줄었다. 첫 블록 묶음의 동기 마운트 중앙값은 2.36초에서 약 0.19초였다(변경 후 3회 측정값 184·185·195ms). 변경 후 영문본은 20회에 걸쳐 나머지 블록을 붙였다. 이 시간은 파싱·페이지 배치·전체 열기와 구분해서 측정했다.
- 두 DOCX 모두 마지막 블록 도착, 편집 후 실행 취소, 수정 없이 저장한 파일과 원본의 바이트 일치를 확인했다. 원본의 중첩 표 문단 6개에 시험용 번역을 한 트랜잭션으로 병기하고 6개를 다듬었다. 다시 연 DOCX에서 변경 추적 정보와 최종 문구를 확인했다.
- Electron에서 합성 한영 문서 세 개를 색인하면서 10ms 타이머를 관찰했다. 3회 측정한 최대 간격의 중앙값이 93ms에서 11ms로 바뀌었다. 색인 완료 시간 중앙값은 243ms와 240ms였다.
- 64MiB HWP 사본으로 워밍업 뒤 기존 검사와 새 검사를 번갈아 5회씩 실행했다. 열기 전 보존 정보 검사 중앙값은 177ms와 64ms였다. HWPX, 변경 추적, 메모, 필드, 복구는 HWP 테스트 묶음에서 확인했다.
- 슬라이드 45장 중 1장을 숨긴 검증 문서를 숨은 창에서 PDF로 출력했다. 출력 44쪽의 그림 색상이 원본과 일치했고 마지막 장의 두 단계 중첩 그룹 그림도 보존됐다.
- 긴 PDF는 줌·페이지 크기에 맞춘 누적 위치표로 현재 행을 찾는다. 2,000쪽 마지막 위치를 찾는 회귀 테스트에서 시작 위치를 읽는 횟수는 최대 11회다. 숨은 시트의 화면 타이머는 중단하고 다시 보이는 시트에서 하나만 시작한다. 4,000문단 워드의 같은 선택 범위를 채팅 입력 중 100회 읽는 실험에서 문서 직렬화가 100회에서 1회로 줄었다.

워드 전체 테스트 4,361개, PDF 전체 테스트 1,849개, 슬라이드 전체 테스트 1,960개, 한글 전체 테스트 1,231개가 통과했다. 후속 변경은 해당 경로의 테스트를 다시 돌렸다. 검색 워커는 관련 테스트 230개와 빌드 산출물의 색인·재색인·삭제로 확인했다. 열기 중 오류가 발생하는 경우에는 부분 문서의 저장·메일 머지·내보내기·AI 요청을 막고, 남은 블록 추가를 재시도할 때 입력과 실행 취소를 보존하는 회귀 테스트를 추가했다.

계측 환경은 Apple M2다. 실제 저사양 Windows 장비에서의 앱 시작부터 첫 입력까지 걸린 시간과 장시간 사용 시 메모리 변화는 별도 확인 대상이다.
