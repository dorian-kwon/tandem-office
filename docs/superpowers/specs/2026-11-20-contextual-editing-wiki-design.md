# 완성본에서 배우는 번역 위키

2026-11-20 채택. 첫 버전은 완성본과 로컬 어휘 검색을 사용한다. 제품·논문 비교와 한↔영 품질 실험 조건은 [조사 노트](../notes/2026-11-20-translation-memory-research.md)에 있다.

## 번역할 때 답해야 하는 질문

부산시 관광 안내서에서 ‘팸투어’를 만났다. 번역가에게 필요한 것은 관광의 정의보다 **이 발주처의 지난 안내서에서는 어떻게 썼는지**, **첫 등장과 이후 표기가 같았는지**, **일정표와 본문에서도 같은 표현이 자연스러운지**다. 이 질문에 이전 완성본의 실제 용례로 답한다. 직접 타이핑했든 AI에 다듬기를 요청했든 저장된 최종 표현만 근거로 삼는다. 첫 번역 그대로 끝난 문서도 완성본에 포함한다. 완성본에 쓰인 표현만으로 사용자가 그 표현을 직접 골랐다고 추론하지 않는다.

## 어떤 항목으로 나누는가

| 항목                          | 보관할 근거                                                                                                                           | 다음 번역에서의 쓰임                                                                                           |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 용어·명칭                     | 원문 표기와 별칭, 도착어 표기, 언어 방향, 의뢰 기관, 분야, 실제 사용 위치. 약칭과 첫 등장 풀어쓰기처럼 조건이 있으면 해당 용례도 연결 | 같은 뜻·같은 조건에서 이전 표기를 찾는다. 기관이나 뜻이 다르면 표기를 나란히 보관한다.                         |
| 문체·표기 관례                | 완성본의 짧은 예문과 그 문장의 역할. 제목·본문·일정표·주의문을 구분하고 관찰한 어조, 종결형, 날짜·단위 표기 등을 기록                 | 같은 기관의 자료에서도 대외 홍보 문구와 실무 보고서, 안내 본문과 표 안에서 각각 어울리는 예문을 찾는다.        |
| 원문과 번역문이 짝지어진 예문 | 양쪽의 짧은 문장·구절, 언어쌍, 문서 판, 검증된 대응 위치                                                                              | 완전히 반복된 문구와 비슷한 문장의 번역 전례를 찾는다. 수치·날짜·고유명은 반드시 현재 원문을 기준으로 한다.    |
| 완성본                        | 문서 제목·언어·독자·의뢰 기관·문서 종류·분야, 구성, 위 항목들의 출처 위치                                                             | 다른 페이지의 증거이자 비슷한 문서를 찾는 진입점이 된다. 도착어로만 작성된 완성본도 구성과 문체의 근거가 된다. |

기관·산업군·문서 종류는 독립된 분류 축이다. 한 가이드북을 ‘부산시’, ‘관광’, ‘방문객용 안내서’ 어느 경로로도 찾을 수 있다. 언어 방향과 대상 지역, 문서 안에서의 역할은 용례에 붙인다. 분류는 프로젝트 정보와 문서의 명시적 단서를 먼저 활용한다. 문서에 등장하는 기관을 발주처로 단정하지 않는다. 근거가 약하면 미분류로 남기고 사용자가 나중에 고칠 수 있게 한다. 기관의 별칭을 합치거나 잘못 연결된 항목을 분리해도 기존 출처 링크는 유지한다.

## 어느 순간에 만드는가

1. **문서에서 나가기, 문서 닫기, 내보내기 성공**이 처리 계기다. 단순한 포커스 이동·타이핑·자동 저장·실행취소·AI 요청마다 수집하지 않는다. 나가기와 닫기에서는 앱의 저장 여부가 결정된 뒤 마지막으로 디스크에 확정된 판을 사용한다. 버린 변경은 포함하지 않는다. 닫기를 취소하거나 내보내기에 실패하면 그 동작으로 새 판을 기록하지 않는다.
2. 위 시점에는 문서 식별자·저장 판·확인할 위치만 작은 로컬 대기 목록에 기록한다. 닫기와 내보내기 완료는 문서 읽기, 분류, Markdown 작성, 모델 응답을 기다리지 않는다. 저장된 적 없는 문서를 변경 사항과 함께 버리면 수집할 결과가 없다.
3. 별도 작업자가 저장된 파일을 읽는다. 최근 저장 뒤 경로나 내용이 달라졌다면 그 위치의 다른 파일을 이전 판의 근거로 쓰지 않는다. 같은 완성본의 내보내기·닫기가 연달아 와도 중복 사례를 만들지 않는다. 형식만 바뀐 산출물은 관계가 확인되면 같은 문서의 출력으로 연결한다.
4. **앱을 다시 실행하면** 로컬에 기록한 판별 상태를 확인한다. 완료한 판은 건너뛰고 대기 중·처리 중 끊긴 판은 이어간다. 원본이 사라지면 ‘원본 확인 필요’를 표시한다. 새 페이지와 근거·색인을 함께 반영한 뒤에만 완료로 표시한다. 완료·대기·확인 필요 상태와 마지막 처리 판은 사용자가 볼 수 있다. 시작할 때 이전 문서를 전수 개봉하지 않는다.

## 무엇을 읽고 어떻게 찾는가

기존 형식별 읽기 경로에서 문단, 중첩 표의 셀, 시트·셀, 그룹 도형, PDF 텍스트 블록 등 필요한 부분을 읽어 위치와 함께 반환한다. 원본을 그대로 보존하고 **검색용 위키 페이지만 Markdown으로 표현한다.** 완성본 전체를 Markdown 사본으로 보관할 필요가 없다. PDF의 스캔 쪽은 사용 가능한 기존 OCR 텍스트를 활용하며, 근거를 읽을 수 없는 쪽은 표시한다.

원문과 번역문은 기존 번역 산출물의 연결 정보, 검증된 병기 셀, 확인 가능한 원문 지문과 위치로 대응시킨다. 같은 단어가 들어 있는 두 문장이나 서로 이웃한 두 셀만으로 용어 대응을 확정하지 않는다. 문장 대응이 확실해도 그 안의 용어 관계가 불분명하면 병렬 예문까지만 기록한다. 원문이 없으면 최종 문장의 문체·표기·구성만 활용한다.

번역과 다듬기에서는 **이번 원문 묶음 → 관련 용어나 병렬 예문 → 이번 독자와 문장 역할에 맞는 문체** 순서로 조회한다. 프로젝트의 용어집과 명시된 지침을 먼저 반영한다. 다음으로 언어쌍·의미·기관·문서 종류·역할이 맞는 용례를 고른다. 한 번 쓰인 표현에는 ‘이 문서의 사례’라고 표시한다. 독립된 완성본에서 일관된 표기가 반복되면 그 범위에서 더 높은 순위로 참고한다. 같은 문서의 여러 판은 한 문서로 센다. 기관 전용 표기와 해당 기관 문서의 발췌는 다른 기관의 요청에 제공하지 않는다. 일반 문체를 산업군 단위로 참고할 때에도 특정 기관의 문구가 노출되지 않게 한다. 충돌하거나 문맥이 애매하면 후보로 제안하고, 관련 사례가 없으면 평소처럼 번역한다.

LLM은 허용된 범위에서 순위가 매겨진 짧은 항목과 출처 ID를 먼저 읽고 필요할 때 해당 예문만 조회한다. 사용자는 같은 출처에서 원문 위치를 열거나 항목의 분류를 고치고 사례를 제외·삭제할 수 있다. 삭제한 문서가 앱 재실행 때 다시 수집되지 않도록 해당 판의 제외 상태를 보존한다. 수집·참고 설정은 로컬에서 제어한다.

## 번역 중 현재 문서의 문맥

완성본 위키는 과거 문서의 전례를 제공한다. 현재 문서를 번역하는 동안에는 별도로 문서 개요와 독자·목적, 고정 표기·약칭·첫 등장, 같은 절의 앞뒤 원문, 확정된 인접 번역을 참고한다. 짧은 표 셀에는 표 제목과 행·열 머리글, 슬라이드에는 제목과 그룹 역할을 함께 준다. 생략이나 지시어를 해석할 때에는 뒤에서 밝혀지는 단서를 쓴다. 제목에서 시작한 비유나 멀리 떨어진 정의는 개요와 해당 부분의 근거 위치를 통해 찾아간다.

전체 번역을 시작할 때 원문의 구조와 대표 구간을 읽어 개요를 만든다. 독자와 목적은 원문에 명시된 근거가 있을 때 기록한다. 같은 문서에서 번역 표현을 다듬거나 중단한 작업을 이어갈 때 그 근거를 재사용하고, 다음 배치의 표현은 현재 적용된 번역에서 확인한다.

전권 번역을 요청하면 기존 번역 단위를 수집할 때 원문 지문별 위치 목록도 만든다. 유니코드·개행 등 표시 차이만 정규화하고 숫자·단위·대소문자·서식 자리표시자는 보존한다. 반복 후보마다 소속 절, 표 머리글, 문장 역할, 언어 방향과 적용 용어집을 함께 비교한다. 같은 철자가 다른 의미로 쓰인 경우는 독립 단위다. 단일 문자열을 문서 전체에서 찾아 한꺼번에 교체하지 않는다.

각 배치는 번역할 단위 ID와 읽기 전용 참고 구절을 나눠 전달한다. 예를 들어 1~~20번을 적용한 뒤 21~~40번을 보낼 때 직전 18~~20번의 원문과 **현재 문서에 실제 반영된 번역문**을 붙인다. 이번 원문에 반복 후보가 있다면 멀리 떨어져 있는 같은 문장의 확정 번역도 해당 위치와 함께 넣는다. 예문의 수는 요청 예산과 절 경계에 따라 조절한다. 모델은 21~~40번의 ID에만 결과를 내고 앱도 그 범위만 적용한다. 현재 문맥에서 뜻이 달라지거나 사용자가 표현을 바꾼 곳은 그대로 복사하지 않는다. 같은 절의 앞 번역이 다음 배치에 꼭 필요하면 그 배치는 순서대로 진행한다. 독립된 절은 기존 병렬 처리를 유지한다.

영문 홍보문에서 가까운 소개 문장들이 같은 주어나 상투적 서두로 시작하면, 정보 초점·문장 구조를 바꾸거나 중복되는 도입부를 덜어낼 수 있다. 기관명·전문용어·UI 명령·안전 지침과 목록의 의도적인 병렬 구조는 일관성을 우선한다. 동의어를 써서 원문의 ‘가능’이 ‘필수’로 바뀌거나 지칭 대상이 달라지지 않도록 한다. 반복 통계는 검토 후보를 찾는 단서로만 쓴다.

문서 전체를 요청마다 넣는 대신 기존 구조 읽기에서 개요와 구간 위치를 가져오고, 완료된 번역 묶음의 결과에서 현재 절의 문장 시작·약칭·주요 표현을 짧게 유지한다. 다음 묶음에서 필요한 근거만 예산 내로 읽는다. 같은 절에서 여러 묶음을 동시에 처리하면 인접 결과는 아직 미확정이므로, 절 완료 후 묶음 경계까지 이어 읽고 표시된 구절만 원문과 대조한다. 직접 편집·실행취소·중단 재개 뒤에는 현재 문서 판과 지문을 확인해 바뀐 구간만 갱신한다. 이 작업 기록은 완성본 위키에 누적하지 않는다. 문단·셀별 Undo와 기존 번역 배치를 유지하고, 이미 사람이 손본 부분은 별도 다듬기 요청 범위에서만 바꾼다.

## ‘위키 보기’에서 Obsidian으로 열기

번역 화면의 **위키 보기**는 이 사용자 프로필의 번역 위키 첫 페이지를 Obsidian으로 연다. 첫 페이지에서 기관·산업군·문서 종류별 목록과 출처가 있는 용어·문체·병렬 예문 페이지로 이동한다. 디스크의 실제 Markdown 파일과 상대 링크로 구성하며, 빈 위키도 첫 페이지가 열린다. SQLite와 원본 자료는 보관함 밖에 둔다. 위키 갱신은 앱이 생성한 파일만 대상으로 한다. Obsidian에서 추가한 개인 노트와 사용자가 수정한 내용은 보존한다.

- 이미 연결한 PC에서는 앱이 관리하는 첫 페이지의 인코딩한 절대 경로로 Obsidian을 호출한다. 같은 이름의 다른 보관함을 열지 않는다.
- Obsidian이 없으면 버튼을 누른 즉시 운영체제에 맞는 공식 설치 파일 다운로드를 호출한다. 직접 배포 경로를 확인할 수 없는 환경은 공식 다운로드 페이지로 연결한다. 설치 뒤 Tandem으로 돌아오면 대기해 둔 열기 요청을 한 번 이어간다. 사용자 취소·오프라인·재실행·중복 클릭 때 다운로드가 반복되지 않게 한다.
- 처음 연결하는 보관함은 Obsidian의 보관함 선택 화면에서 **폴더를 보관함으로 열기**를 사용한다. Tandem은 준비해 둔 폴더 경로와 복사 동작을 제공한다. 설치됐지만 URI가 등록되지 않은 경우 앱 첫 실행과 재시도를 안내한다. 정상 사용 중에는 설치 여부를 반복 확인하지 않는다. [Obsidian URI](https://help.obsidian.md/Extending+Obsidian/Obsidian+URI) · [공식 다운로드](https://obsidian.md/download)

## 대용량 문서와 성능 계약

- 편집·열기·스크롤·채팅 입력·Undo/Redo 경로에 위키용 이벤트 감시나 문서 복사를 추가하지 않는다. 입력 중에는 원문 대조, 전체 파일 해시, 분류 모델 호출을 실행하지 않는다.
- 개인 프로필에 로컬 SQLite 색인을 두고 백그라운드 작업자가 한 번에 한 문서를 제한된 메모리로 처리한다. 앱이 바쁠 때는 작업을 양보하고, 처리 지점을 저장해 다시 이어간다. 지연·잠금·디스크 부족이 문서 저장이나 닫기를 실패시키지 않게 한다. 기록 실패는 상태에 표시한다.
- 참고 자료는 기존 번역 묶음과 토큰 예산 안에서 조회한다. 추가 AI 왕복 없이 기본 검색을 끝내고, 로컬 조회가 지연되면 현재 요청은 기다리지 않고 진행한다. 위키 항목 수가 늘어도 전체 위키를 읽거나 모델에 보내지 않는다.
- 검증에서는 같은 빌드에서 기능 켬·끔을 교차 비교한다. 저사양 조건의 첫 열기, 입력·스크롤·번역 중 입력, 저장·닫기·내보내기, 다음 실행, 메모리까지 확인한다. 위키 때문에 UI 스레드에 50ms 이상 작업이 생기면 실패로 본다. 입력·스크롤 p95 추가 지연은 60Hz 한 프레임(약 16.7ms) 이내를 상한으로 삼고, 반복해서 드러나는 체감 지연은 상한 안에서도 고친다. CPU·메모리는 색인 대기 중과 색인 실행 중을 따로 비교한다. 수치는 검증 목표다.

## 인수 시험

- 같은 기관·같은 종류, 같은 기관·다른 독자, 다른 기관·같은 산업, 다의어·기관 별칭·미분류, 언어 방향 반대, 현 용어집과의 충돌을 독립된 완성본으로 시험한다. 각 결과에 근거가 붙는지 확인한다.
- 완성본 100편 이상·사례 10만 건에서 검색 지연과 결과 크기를 측정한다. 중간 번역·직접 타이핑·다듬기·되돌리기에서 사례가 쌓이지 않고, 나가기·닫기·내보내기 뒤 마지막 저장 결과만 남는지 확인한다. 닫기 취소, 저장 안 함, 내보내기 실패, 중복 이벤트, 종료 직후 재실행, 색인 중 강제 종료, 파일 이동·삭제도 시험한다.
- 숨김 Electron으로 지원 파일 19종의 열기·저장·번역 산출물 경로와 기존 편집 단위 Undo/Redo를 검사한다. 실제 부산 가이드북 DOCX와 용어집, 500쪽 HWP·HWPX와 PDF, 대용량 시트, 중첩 표·그룹을 포함한다. 문서별로 확인 가능한 위치까지만 위키화하는지 대조한다. 기존 번역 배치와 원본 보존도 확인한다.

현재 프로젝트 문체와 언어는 `packages/translate-project/src/project-file.ts`, 요청별 용어집·참고자료 예산은 `apps/shell/src/main/translate/context-injection.ts`가 담당한다. 로컬 SQLite 검색은 `apps/shell/src/main/file-index/store.ts`에 선례가 있다. 단독으로 연 문서에도 같은 규칙을 적용하고 확인할 수 없는 프로젝트 정보는 미분류로 둔다.
