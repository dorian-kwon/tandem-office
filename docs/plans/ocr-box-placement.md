# OCR 박스 배치 계획

상태: 설계(승인 대기). 대상: 번역 프로젝트의 그림 OCR(`apps/shell`)에서 docx 안의 그림.

## 의도와 이유

번역 프로젝트에서 docx·xlsx에 박힌 그림을 OCR하면, 지금은 읽은 글을 "그림 뒤 문단 / 문서 끝 / 표 칸 / 엑셀 칸 / 새 시트" 중에서 골라 **글만** 놓는다(`OcrPlacementDialog`, `ocr-placement.ts`). 그림 속 글이 원래 있던 자리와 크기는 사라진다.

바꾸려는 것: 글자가 있는 부분마다 **그림 위에 박스**를 놓고, 박스마다 읽은 글을 넣는다. 글자 크기도 AI에게 받아 폰트를 맞춘다. 이렇게 놓은 글은 번역할 때 번역 대상에 들어간다.

## 목표

- AI가 한 번의 읽기로 글, 박스 위치·크기, 글자 크기를 함께 돌려준다.
- 배치 화면에서 사람이 그림 위에 겹친 박스를 확인한다. 박스를 옮기고, 크기를 바꾸고, 지우고, 추가하고, 글을 고칠 수 있다.
- 확정하면 docx의 그림 위에 박스 모양 텍스트 상자로 쓴다. 상자 하나는 글자가 있는 부분만 덮고, 폰트 크기는 읽은 글자 크기에 맞춘다.
- 이렇게 쓴 상자 안의 글이 번역에 들어가고, 번역 결과 docx에도 상자와 폰트 크기가 남는다.
- 박스를 얻지 못하면 지금의 목록 배치로 돌아간다(기능이 줄지 않는다).

## 범위 밖

- xlsx 박스 배치(1단계 뒤). xlsx 도형 안의 글을 번역이 읽는지 아직 확인하지 못했다.
- 번역 결과 docx를 다시 그림에 합성(번역문을 그림 픽셀에 굽기).
- PDF 앱의 OCR(보이지 않는 글자 층)과 AI 채팅의 OCR 팝업(`selectOnly`)은 바꾸지 않는다.
- 로컬 OCR 엔진(Vision, Windows.Media.Ocr)으로 박스를 얻는 길(결정 0102가 배제).

## 하지 말아야 할 것

- 그림 전체를 한 상자로 덮는 것.
- 사람이 확인하기 전에 문서에 쓰는 것. 배치는 지금처럼 사람의 확정으로만 쓴다.
- 박스를 못 얻었다고 읽은 글까지 버리는 것.
- 원본 그림을 지우거나 바꾸는 것.

## 지금 코드가 하는 일

- OCR 결과 `OcrPageResult.payload`는 문단·줄·표·캡션 텍스트뿐이고 좌표가 없다. 읽기 지시문(`packages/pdf-structure/src/ai-read/instruction.ts`)은 "그림 속 글은 옮기지 말고 [FIGURE]로 적으라"고 한다. 번역 OCR은 같은 지시문으로 그림을 읽는다.
- 배치는 `apps/shell/src/main/translate/ocr-placement.ts`가 docx XML에 문단을 끼워 넣거나 xlsx 칸에 값을 쓴다.
- docx 번역 엔진(`packages/docx-engine/src/generate.ts`)은 `w:txbxContent`(텍스트 상자) 안의 문단을 이미 번역한다.
- AI 호출은 `OcrAsk`(`shared/translate-ocr.ts`)이며 요청은 `AiReadRequest`, 결과는 메인이 다시 검사한다.

## 이 저장소의 제약(읽고 확인한 것)

- 결정 0102: OCR은 AI로만 하고, 이 PC에서 도는 OCR 프로그램은 넣지 않는다. 그래서 아래 B안은 이미 배제된 길이다. 이 계획은 0102를 뒤집지 않고 "AI가 위치도 돌려준다"를 더하는 새 결정(결정 기록 추가)으로 다룬다.
- 보내는 것과 비용은 지금과 같아야 한다. 그림 한 장에 AI 호출 한 번이고, 박스 읽기는 기존 읽기 요청을 **대체**한다(호출을 더하지 않는다). 확인 화면의 "보낼 수·쓸 AI·요금" 문구와 사람이 고른 쪽만 읽는 규칙은 그대로다.
- `packages/pdf-structure`의 보관소 형식과 열쇠 모양은 바꾸지 않는다. 바꾸면 이미 보관된 결과를 잃는다. 박스 결과가 보관소에 들어간다면 형식 번호를 올리고 옮기는 길을 만든다. 보관소에 넣지 않고 배치 확정 전까지 메모리에만 두는 것이 더 작은 길인지 먼저 살핀다.
- `packages/docx-engine`은 이 계획에서 고치지 않는다. 박스는 `apps/shell/src/main/translate/ocr-placement.ts`가 docx XML에 쓴다. 확인 중 문서 엔진을 고쳐야 한다면 멈추고 사람에게 묻는다(`CLAUDE.md`). 저장된 문서 안의 식별자와 보조 파일 이름은 바꾸지 않는다.
- 화면 문구는 21개 언어를 모두 채운다(`apps/shell/src/renderer/src/i18n/translate/<언어>.ts`, 한국어·영어는 직접 쓰고 나머지는 번역). 코드와 주석은 영어다. 검사는 `npm run check:english-comments`와 합치기 전 검사다.
- 화면 색은 `docs/standards.md`의 "화면 색" 규칙을 따른다(`npm run check:theme-colors`). 박스 겹침 표시도 해당된다.

## 접근

세 가지를 놓고 비교했다.

- A. AI가 글과 함께 박스 좌표·글자 크기를 돌려준다. 모든 플랫폼에서 되고 지금 연결을 그대로 쓴다. 모델에 따라 좌표가 어긋날 수 있다.
- B. 로컬 OCR 엔진이 박스를 주고 AI는 글만 읽는다. 박스는 정확하나 Linux와 도우미 없는 빌드에서 안 되고, 두 결과를 맞춰야 한다.
- C. 사람이 직접 박스를 긋는다. 가장 정확하나 그림이 많으면 번거롭다.

**선택: A.** 어긋남은 배치 화면에서 사람이 박스를 고치는 확인 단계로 흡수한다. 선택한 사람: 사용자(대화에서 정함).

## 정해진 것

- 박스마다 받는 값: 글, 위치(왼쪽·위), 크기(너비·높이), 글자 크기. 좌표는 그림 크기에 대한 비율로 받는다(그림이 문서에서 다른 크기로 놓여 있어도 쓸 수 있게).
- 폰트 크기는 읽은 글자 크기를 문서에 놓인 그림 크기에 곱해 포인트로 환산해 맞춘다.
- 쓰는 방식은 박스 모양 텍스트 상자다. 글자가 있는 부분만 덮는다.
- 지금의 목록 배치는 남겨 두고, 박스를 얻지 못했을 때와 사람이 고를 때 쓴다.
- 1단계는 docx만 한다.

## 설계자가 정한 것(검토에서 나온 질문의 답, 사용자가 맞다고 확인함)

- **박스 응답의 글.** 박스마다 글이 들어 있고, 사진 전체의 읽은 글은 박스 글을 읽는 순서대로 이어서 만든다. 그래서 박스가 비거나 걸러져도 글이 남아 목록 배치로 돌아갈 수 있다. 호출은 늘리지 않는다. 응답이 형식에 맞지 않으면 지금의 규칙(한 번 다시 묻고, 그래도 안 되면 그 그림은 읽지 못한 것으로 둔다)을 따른다. 낡은 지시문으로 한 번 더 부르는 길은 만들지 않는다(요금 문구가 바뀌기 때문).
- **박스 하나의 크기.** 눈으로 한 덩어리인 글 영역(줄 한 줄이거나, 같은 문단·같은 라벨의 이어진 줄들)을 한 박스로 한다. 낱말 단위나 그림 전체는 아니다. 번역은 박스 단위로 되므로 문장이 줄마다 끊기지 않게 한다. 박스 수 상한과 겹침 걸러내기는 이 기준으로 만든다.
- **1단계에서 지원하는 그림.** 본문 문단 안의 회전·잘라내기가 없는 줄 안 그림(`wp:inline`)만 한다. 잘라낸 그림, 회전한 그림, 이미 떠 있는 그림(`wp:anchor`), 머리말·꼬리말·표·텍스트 상자 안의 그림은 박스를 놓지 않고 지금의 목록 배치로 보내며, 화면에 이유를 한 줄 알린다. 이 범위는 나중에 넓힌다.

## 박스의 바탕(결정)

불투명 바탕으로 한다. 그림 속 원래 글은 그림 픽셀에 그대로 남아 있어서, 바탕이 없으면 번역문이 원문 위에 겹쳐 읽기 어렵다. 박스는 글자가 있는 부분만 덮고, 그림 파일 자체는 바뀌지 않는다(박스를 지우면 원본 그림이 그대로 보인다). 바탕색은 만드는 사람이 정한다(그림 배경에서 뽑거나 흰색). 사용자는 추천을 따르라는 뜻으로 "해줘"라고 답했다. 바탕이 가리는 원문을 보고 싶다는 요구가 나오면 투명 옵션을 더하는 것은 이 계획의 범위 밖이다.

## 승인

설계는 승인됐다(사용자 답: "해줘", 2026-11-14). 다음은 구현 계획이다.

## 만드는 사람이 정할 것(제 판단, 근거 포함)

- 박스 요청의 지시문과 응답 형식. 기존 읽기 지시문과 별개로 두는 것을 권한다. 기존 읽기는 위치 없는 글을 만드는 경로라 섞으면 다른 쓰임을 해친다. 새 응답을 검사하는 `payload`도 박스용 형태를 따로 둔다.
- 좌표가 그림 밖이거나 서로 크게 겹치거나 글이 비는 박스를 어떻게 거를지.
- 그림 위에 상자를 겹치는 docx 표현. 그림을 건드리지 않고 상자만 위에 놓는 방법과, 그림과 상자를 하나의 묶음으로 만드는 방법을 비교해서 고른다. 두 방법 모두 Word와 LibreOffice에서 보이는지 확인한다. 이 선택이 가장 위험하다.
- 번역문이 원문보다 길어질 때 상자 안에서 줄이는 방법(자동 맞춤 또는 폰트 줄이기).
- 배치 화면의 박스 편집 조작(끌기, 모서리 크기 조절, 삭제, 추가)과 21개 언어 문구, 접근성.
- 한 그림에 박스가 너무 많을 때의 상한.

## 확인해야 할 것

- 박스로 놓은 글이 번역 프로젝트의 번역에 실제로 들어가고 결과 docx에 상자·폰트 크기가 남는다. 이를 단위 테스트와 실제 docx로 확인한다.
- Windows에서 실제 구독 AI로 읽어 박스가 그림의 글과 맞는지는 사람이 확인한다(OCR과 같은 방식으로 단위 테스트로는 다 못 본다).
- 이 저장소의 규칙: 결정 기록 추가, `docs/architecture.md`·`docs/contracts.md`·`apps/shell/AGENTS.md` 갱신, 합치기 전 검사(`docs/standards.md`).
