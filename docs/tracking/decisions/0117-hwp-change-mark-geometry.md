# 0117. 한글 변경 표시의 쪽 좌표는 문서가 바뀔 때 다시 구한다

- 날짜: 2026-11-18
- 상태: 채택

## 배경

이전 조사에서 한글 문서가 CPU를 오래 쓰던 프로필을 다시 확인했다. 한 프로필에서
`getSelectionRectsInCellByPath` 아래의 표본이 89.9%였다. 호출자는 AI 표 읽기 도구가
아니라 `drawMarks`가 변경 표시의 좌표를 구하는 `marks.flatMap`이었다. 최대 500개
표시를 문서 변경 직후, 350ms 뒤, 화면 크기가 바뀔 때마다 전체 쪽에서 다시 찾았다.

## 결정

앱의 `studio-plugin/agent-plugin.mjs`에서만 고친다. 문서 엔진과 저장 형식은 바꾸지 않는다.

- 일반 행의 셀은 실제 시작·끝 커서의 쪽 번호를 엔진의 기존 경로 기반 선택 조회에
  힌트로 넘긴다. 제목 줄 반복이 켜진 표도 행별로 구분한다. 제목 셀의
  `row + rowSpan` 최댓값까지는 같은 행의 일반 셀과 합친 셀이 덮는 행을 포함해
  완전한 경로 조회를 유지하고, 그 뒤의 일반 행에만 힌트를 쓴다. 제목 행 사이에
  빈틈이 있어도 최댓값 앞을 모두 제외하는 보수적인 판정이다.
- 표의 행·제목 메타데이터는 좌표를 갱신하는 동안 표마다 한 번만 읽으며, 한 표의
  셀 2,000개를 상한으로 둔다. 중첩 표, 상한 초과, 불완전한 메타데이터, API 부재,
  커서의 쪽 정보 조회 실패는 기존 전체 조회로 돌아간다.
- 쪽 안의 좌표를 보관하고, 확대와 반복 그리기에서는 화면상의 위치만 다시 계산한다.
  문서 변경과 표시 목록 갱신, 조판이 안정될 시간을 둔 한 번의 갱신에서는 좌표를 다시 구한다.
  확대가 그대로인데 페이지 컨테이너 크기가 달라졌다면 늦은 조판으로 보고 다시 구한다.
- 화면 크기 관찰 자체가 350ms 예약을 계속 만들지 않는다. 플러그인을 끄면 예약도 취소한다.

## 확인 범위

실제 WASM 엔진으로 합성 문서를 만들어 비교했다. 31쪽 문서의 뒤쪽 셀 첫 조회는
전체 조회 약 22ms, 커서 두 개와 힌트 조회 합계 약 1.8ms였고, 반환 좌표는 같았다.
시간은 이 Mac에서 한 측정값이며 모든 문서의 성능을 뜻하지 않는다.

회귀 시험은 반복 그리기의 조회 횟수, 수정 후 재조회, 종료 후 예약 취소, 일반 셀의
좌표 일치, 같은 제목 행의 일반 셀과 합친 제목 셀이 덮는 행의 보호, 메타데이터 상한과
조회 실패의 기존 경로, 여러 쪽에 걸친 셀의 모든 표시를 확인한다. 기존 공개 견본의
48개 셀 문단도 별도 비교에서 좌표가 일치했다.

2026-11-18에는 사용자가 제공한 실제 HWP 원본을 별도 엔진 프로브로 읽어 추가 확인했다.
파일은 723,584,512바이트, 74쪽이며 112개 표의 `repeatHeader`가 모두 켜져 있었다.
전체 2,902개 셀 중 제목 셀은 41개이고, 행별 판정은 일반 셀 2,861개(98.59%)에
힌트 경로를 적용할 수 있었다. 표 메타데이터 조회는 한 측정에서 78.85ms였다.
대표 전체 셀 범위 276개의 힌트 조회와 전체 조회가 같은 좌표를 반환했다.

별도로 고른 8개 범위를 조판 후 세 차례 조회한 합계는 5,363.72ms에서 145.26ms로
줄었다(해당 표본에서 약 36.9배). 뒤쪽 100번 표의 측정은 1,696.47ms에서 33.45ms였다.
최초 조판 약 1.46초는 남는다. 이 수치는 해당 Mac·문서·범위의 엔진 조회 측정이며,
앱 전체나 모든 문서의 CPU 개선 배율을 뜻하지 않는다. 원본은 앱의 512MiB 열기 한도를
넘으므로 당시 확인은 앱 화면에서 정상적으로 열었다는 뜻도 아니다.

중첩 표와 실제 반복 제목 행의 첫 좌표 계산 비용은 남지만, 같은 상태의 반복 계산은
피한다. 이 결과는 BMP 변환 사본의 검증과 별개이며 엔진이나 저장 바이트를 고치지 않는다.
