# 0117. 한글 변경 표시의 쪽 좌표는 문서가 바뀔 때 다시 구한다

- 날짜: 2026-11-18
- 상태: 채택

## 배경

이전 조사에서 한글 문서가 CPU를 오래 쓰던 프로필을 다시 확인했다. 한 프로필에서
`getSelectionRectsInCellByPath` 아래의 표본이 89.9%였다. 호출자는 AI 표 읽기 도구가
아니라 `drawMarks`가 변경 표시의 좌표를 구하는 `marks.flatMap`이었다. 최대 500개
표시를 문서 변경 직후, 350ms 뒤, 화면 크기가 바뀔 때마다 전체 쪽에서 다시 찾았다.

## 결정

앱의 `studio-plugin/agent-plugin.mjs`에서만 고친다. 문서 엔진과 저장 형식은 바꾸지 않는다.

- 일반 표의 셀은 실제 시작·끝 커서의 쪽 번호를 엔진의 기존 경로 기반 선택 조회에
  힌트로 넘긴다. 중첩 표와 제목 줄 반복 표는 완전한 경로 조회를 유지한다. API가 없거나
  쪽 정보를 얻지 못하면 기존 조회로 돌아간다.
- 쪽 안의 좌표를 보관하고, 확대와 반복 그리기에서는 화면상의 위치만 다시 계산한다.
  문서 변경과 표시 목록 갱신, 조판이 안정될 시간을 둔 한 번의 갱신에서는 좌표를 다시 구한다.
  확대가 그대로인데 페이지 컨테이너 크기가 달라졌다면 늦은 조판으로 보고 다시 구한다.
- 화면 크기 관찰 자체가 350ms 예약을 계속 만들지 않는다. 플러그인을 끄면 예약도 취소한다.

## 확인 범위

실제 WASM 엔진으로 합성 문서를 만들어 비교했다. 31쪽 문서의 뒤쪽 셀 첫 조회는
전체 조회 약 22ms, 커서 두 개와 힌트 조회 합계 약 1.8ms였고, 반환 좌표는 같았다.
시간은 이 Mac에서 한 측정값이며 모든 문서의 성능을 뜻하지 않는다.

회귀 시험은 반복 그리기의 조회 횟수, 수정 후 재조회, 종료 후 예약 취소, 일반 셀의
좌표 일치, 반복 제목 표·커서 조회 실패의 기존 경로, 여러 쪽에 걸친 셀의 모든 표시를
확인한다. 기존 공개 견본의 48개 셀 문단도 별도 비교에서 좌표가 일치했다.

원래 신고 문서는 이 환경에 없으므로 그 파일에서의 CPU 수치는 재측정하지 못했다.
중첩 표와 반복 제목 표의 첫 좌표 계산 비용은 남지만 같은 상태의 반복 계산은 피한다.
